# Bootstrap del Nodo Perimetral y Handoff hacia Ansible

> **Navegación**: [← Golden Image](01.5-golden-image.md) | [Hardening →](../)


Definición del procedimiento de transferencia de gobernanza del nodo biomédico perimetral, desde el estado "accesible por SSH" hasta el estado "gobernado por Ansible de forma idempotente", asumiendo la Fase 0 ya completada.

## 1. 📋 Resumen del Proceso

| Parámetro | Definición |
| --- | --- |
| **Estado de entrada** | Nodo accesible vía SSH mediante clave privada del Control Node |
| **Estado de salida** | Nodo gobernado por Ansible con el rol `01_bootstrap` aplicado |
| **Control Node** | macOS con OpenSSH y Ansible instalados |
| **Nodo perimetral** | Raspberry Pi Zero 2 W con DietPi (Fase 0 completada) |
| **Alcance** | Exclusivamente el handoff hacia Ansible; no cubre hardening ni almacenamiento |

## 3. Estrategia de Llaves Criptográficas

- **Llave Pública (`id_ed25519.pub`):** Ya inyectada en `dietpi.txt` durante la Fase 0. No se modifica en este documento.
- **Llave Privada (`id_ed25519`):** Reside exclusivamente en el almacén seguro del Control Node (Bitwarden). **Nunca** se copia a la SD ni a repositorios de código.

## 4. Verificación de Conectividad SSH y Pruebas

Antes de invocar Ansible, se debe verificar desde el Control Node que la clave funciona y que el servidor SSH es OpenSSH (no Dropbear). Para ello, se ejecuta el siguiente comando:

```bash
ssh dietpi@<IP_DEL_NODO> 'hostname && uname -a && sudo ss -tulpn | grep :22'
```

**Validación de la prueba:**
1. `hostname`: Debe devolver el nombre del nodo (`Biomedic-server`).
2. `uname -a`: Debe devolver la arquitectura ARM (ej. `aarch64 GNU/Linux`).
3. `ss -tulpn | grep :22`: **Es el paso crítico.** Debe devolver una línea que contenga `users:(("sshd",...))`. Si por el contrario devuelve `users:(("dropbear",...))`, el sistema tiene Dropbear y Ansible fallará.

Si la verificación falla (Dropbear instalado), se debe intervenir el nodo manualmente para instalar OpenSSH y deshabilitar Dropbear:

```bash
sudo apt update && sudo apt install -y openssh-server openssh-sftp-server
sudo systemctl disable --now dropbear
sudo systemctl restart ssh
```

> ⚠️ Esta verificación es el único punto de control que justifica la intervención del nodo fuera de Ansible. Si la verificación es exitosa, el resto de las acciones se ejecutan vía playbooks.

## 5. Estructura del Proyecto Ansible

La estructura del proyecto Ansible se desacopla en roles para mantener la modularidad. Los playbooks operativos se documentan por separado:

```
ansible/
├── ansible.cfg
├── inventory.ini
├── host_vars/
│   └── biomedic.yml
├── site.yml
└── roles/
    ├── 01_bootstrap/          # Handoff inicial y dependencias
    ├── 02_hardening/          # (Ver: 02-security/ssh-hardening.md)
    ├── 03_storage_luks/       # (Ver: 03-storage/luks-btrfs.md)
    └── 04_biomedic_services/  # (Ver: 04-services/telemetry.md)
```

### 5.1 Configuración (`ansible.cfg`)

```ini
[defaults]
inventory           = inventory.ini
# Ruta donde Ansible buscará los roles
roles_path = roles
host_key_checking   = False
retry_files_enabled = False
interpreter_python  = /usr/bin/python3
pipelining          = True
# Nivel de detalle por defecto (equivale a agregar -v)
verbosity = 1

[ssh_connection]
# Habilita el reenvío de agente y persistencia de conexión
ssh_args = -o ForwardAgent=yes -o ControlMaster=auto -o ControlPersist=60s
```

### 5.2 Inventario Inicial (`inventory.ini`)

Solo define nombres y pertenencia a grupos:

[edge_nodes]
biomedic

[dietpi_hosts]
biomedic
---

### 5.3 Variables por Host (`host_vars/biomedic.yml`)

```yaml
ansible_host: <IP_DEL_NODO>
ansible_port: 22
ansible_user: username_del_nodo
```
### 5.4 Playbook Maestro (`site.yml`)

El archivo `site.yml` actúa como el orquestador principal del proyecto. En esta fase inicial, se debe declarar el rol de `01_bootstrap` y asignarle la etiqueta `bootstrap`. Esto permite que Ansible ejecute exclusivamente esta fase durante el handoff, ignorando los roles de seguridad y almacenamiento que aún no se han desarrollado.

```yaml
---
- name: Configuración inicial del servidor biomédico
  hosts: edge_nodes
  become: yes
  roles:
    - role: 01_bootstrap
      tags: [bootstrap]

    # Roles futuros (se habilitarán en las siguientes fases del proyecto)
    # - role: 02_hardening
    #   tags: [hardening]
    # - role: 03_storage_luks
    #   tags: [storage]
    # - role: 04_biomedic_services
    #   tags: [services]
```

**Justificación técnica de los parámetros:**
*   **`become: yes`:** Se emplea para habilitar la elevación de privilegios (equivalente a `sudo`).

*   **`tags: [bootstrap]`:** Permite el filtrado selectivo.

**Nota sobre la sintaxis:** Se emplea la estructura de diccionario (`- role: nombre_del_rol`) ya que permite asignar atributos adicionales (como los `tags`) de forma explícita y legible.

## 6. Procedimiento de Ejecución del Handoff

Una vez verificada la conectividad SSH, se procede a validar que Ansible puede comunicarse con el nodo y ejecutar el rol de bootstrap.

```bash
# 1. Validación de ping (verificación de conectividad de Ansible)
ansible edge_nodes -m ping

# 2. Ejemplo de ejecución del bootstrap (solo el rol 01)
ansible-playbook -i ansible/inventory.ini ansible/site.yml --tags bootstrap -v
```

Si el comando `ping` devuelve `pong`, el handoff se considera exitoso y el nodo está listo para que se le apliquen los playbooks de seguridad y almacenamiento.
